# 小镇不按剧本走：本地可玩原型实施计划

日期：2026-10-16。状态：已按独立重写路线完成首版本地原型。本文保留规划依据；实际运行方式和实现边界见根目录 README，验证结果见 docs/VALIDATION.md。

后续已实现规则怪谈第一夜、WASD 连续移动与单角色快速对话，详见 `docs/NIGHT_GAME.md`。以下保留庆典首版的原始规划。

## 1. 结论与规划前提

**已确认新建 Python + React 项目，参考 ARTEX 的工程思路，第一版不直接修改或移植 ARTEX。**

你已确认的方向：

- 第一版是能反复试玩、保存和重置的本地原型。
- Python 后端 + React 前端。
- NPC 有独立目标、记忆和信息边界；合作、拒绝、谈判和转述由各自 Agent 决定。
- 世界规则、物品归属、行动合法性和胜负由程序裁决，不预写剧情分支。

本计划暂按单人推进或少量协作、单机单玩家、使用外部模型 API 估算。不沿用原材料中“必须两天完成黑客松”的假设。第一版体验目标是约 10 分钟一局，实际时长取决于模型延迟和玩家阅读速度。

## 2. ARTEX 源码核对与路线选择

本次实际读取了仓库的 README、依赖清单、Worker、Planner、调度器、SSE 和底层 Norma 接口，未安装依赖、编译或运行 ARTEX。参考版本固定为 `1d982abee965563b3cc2e616f6cc766042cb36ac`；下面是静态阅读结论，不代表已验证运行质量。

| 已核对的部分 | 实际特点 | 对本项目的影响 |
| --- | --- | --- |
| Go + Next.js 工程 | 不是 Python 后端，前端也包含大量领域管理页面 | 整体接管不能直接节省游戏核心的开发 |
| `agent/worker.go` | Worker 领取一条 intent；会话标识绑定探索与 intent；执行参数直接依赖资产库、探索库和领域回调 | Worker 不能直接等同于一个持久 NPC；仅更换提示词不够 |
| Worker 工具组装 | 默认加入文件、Shell 等工具，并追加领域工具及扩展 | 游戏应重新定义封闭行动接口，无需继承这一工具集合 |
| `agent/planner.go`、`server/engine.go` | 全局规划、心跳唤醒、领取任务、目标完成与终态处理 | 与“等玩家输入，再推进一个回合”的生命周期不同 |
| Worker 上下文 | 包含全局探索概况 | 与 NPC 私有认知不同，游戏必须重做感知投影 |
| `norma/llm` | 模型协议适配、流式事件、重试与用量信息 | 值得借鉴接口边界；Python 原型无需跨语言复用 Go SDK |
| `server/server.go` | 活动流有历史重放、游标和 SSE 推送 | 可参考事件续传机制，不必搬入整套服务 |
| `LICENSE`、README 许可章节 | AGPL-3.0，README 另有使用声明 | 若以后复制具体实现或做衍生版本，应先核对对应许可；本路线采用独立实现 |

三条路线比较：

| 路线 | 能节省什么 | 需要承担什么 | 结论 |
| --- | --- | --- | --- |
| 直接 fork ARTEX，新增 GameRunner | 部分模型管理、记录、数据库和后台组件 | 学习 Go 与原领域架构，重做游戏状态、角色记忆、调度和主界面 | 如果明确要求基于 ARTEX 参赛，或团队熟悉 Go，才优先考虑 |
| React + Python 游戏服务 + Go Agent 服务 | 保留部分 Go 执行层 | 两个后端、跨进程协议、额外部署和调试 | 第一版收益不足 |
| 新建 Python + React，按需参考机制 | 技术栈统一，所有模块围绕游戏设计 | 自己实现精简模型适配、事件记录和管理页面 | **当前推荐** |

这里“从头做”的范围很小：实现一个微型回合世界及四个角色，不重新造通用 Agent 平台。真正需要的 AI 循环是“组装可见上下文 → 生成一个行动提案 → 校验 → 裁决”，第一版不引入复杂 Agent 框架。

## 3. 第一版具体交付什么

### 游戏：《开幕前十五分钟》

保留你材料中的庆典场景，四个 NPC：镇长、管理员、店主、记者。地图只有广场、商店、舞台，玩家扮演临时志愿者。

标题中的十五分钟是故事设定；程序使用回合推进，界面显示剩余回合。**思考、阅读和等待模型不会扣回合。** 初步默认 18 回合，可配置为 12 / 18 / 24，经过试玩后再确定默认难度。

核心循环：观察现场 → 与角色交谈或采取行动 → NPC 各自决策 → 看到可感知后果 → 下一回合。

必须能完成：

- 玩家移动、观察、交谈、拿取和交付物品、执行场景交互、等待。
- 四个 NPC 各自依据目标、记忆和所见信息行动，也能主动找其他人。
- 店主可以提出条件、拒绝或自行行动；记者可以核实或转述；这些行为不写成固定分支。
- 每一局可保存、恢复、重新开始；可查看已发生事件。
- 单独的调试页面可以查看角色上下文、行动及结果、调用耗时和用量，方便判断 Agent 是否真正起作用。
- 开局可修改角色目标，生成新的一局，比较行为变化。

第一版暂不包含语音、3D、多人联机、无限地图、向量数据库、自动生成世界和长期社会模拟。角色目标允许自然语言修改，但角色能力与世界规则仍由场景配置约束。

### 把谈判条件落实成游戏规则

只让角色提出条件还不够，世界里必须有兑现条件的办法：

| 事物 | 规则与可执行交互 |
| --- | --- |
| 舞台钥匙 | 开局由管理员持有；同地点才能交付；持钥匙者在舞台入口可以开门 |
| 安全检查 | 舞台打开后才能检查；默认管理员具备资格，检查累计占用两个工作回合 |
| 备用音箱 | 开局归店主所有；借用通过实际交付体现；搬到舞台后需要安装，嘴上答应不算安装 |
| 摊位安排 | 开局是待确认；镇长可以在广场用 `allocate_stall` 确认分配；玩家可以促成承诺，不能冒充镇长直接分配 |
| 采访 | 同地点可以进行采访并记录采访事件；承诺采访本身不等于已经采访 |
| 承诺 | 保存“谁向谁说了什么”和相关事件；物品交付、摊位确认等明确条件可按事件判断是否兑现；模糊承诺保留为角色判断 |

开幕成功由“舞台已打开 + 检查已完成 + 音箱已安装可用”决定，最迟在最后一回合所有行动裁决后结算；提前全部完成时允许结束本局。记者报道和角色评价只能引用已有事件，并标注传闻、观点与事实的区别。

诸如“让记者主持五分钟拖延开幕”在第一版可以被讨论，但没有延时规则就不能实际加回合。后续若加入主持、断电、破坏等能力，应先增加规则与行动，再让 Agent 自主使用。

## 4. 技术方案

建议采用：

| 层 | 选择 | 原因 |
| --- | --- | --- |
| 前端 | React + TypeScript + Vite | 适合独立游戏页面，本地开发简单 |
| 界面 | Tailwind CSS；地图先用 SVG / DOM | 三地点、五个角色无需游戏引擎，便于先验证玩法 |
| 后端 | Python + FastAPI + Pydantic | API、结构化输出验证和异步调用集中在同一工程 |
| 存储 | SQLite + SQLAlchemy + Alembic | 单机原型不要求先装 PostgreSQL；模型调用期间不占数据库写锁 |
| 模型 | 小型 Provider 接口，先适配一个选定的模型端点 | 接口只负责结构化决策、超时、用量；不提前做多供应商配置中心 |
| 推送 | SSE + HTTP 动作提交 | 单向事件更新足够，支持重连后按游标补齐 |
| 测试 | pytest；前端关键流程冒烟检查 | 优先验证规则、隔离、并发和恢复，而非 UI 快照数量 |

模型端点通过服务端配置指定，密钥只存在后端。暂不指定模型品牌和价格，先用单角色试验验证中文表现、合法动作率、延迟与每局消耗，再固定演示配置。四个角色可以共用同一模型，不需要四种模型或四个常驻进程。

### 核心模块

```text
React 游戏界面
    │ HTTP：提交动作 / 查询存档     ↑ SSE：玩家可见事件
    ▼
FastAPI
    ├── TurnRunner：回合、唤醒、预算、超时
    ├── Perception：角色及玩家的信息投影
    ├── CharacterAgent：角色配置 + 记忆 → 一个行动提案
    ├── Rules：校验、冲突处理、世界状态变化
    └── Store：快照、事件、记忆投递、模型调用记录
                │
              SQLite
```

只允许 Rules 提交世界状态。模型不知道数据库连接，也没有文件、Shell 或任意网络工具。玩家的台词作为场景内消息传入，不能覆盖角色的系统规则。

## 5. 行动、认知与回合协议

### 行动边界

最小行动集为 `move / observe / speak / take / give / interact / wait`。`interact` 只能引用场景注册的交互，例如 `unlock_stage / inspect_stage / install_speaker / allocate_stall / interview`，不能传任意效果表达式。

角色调用时由服务器绑定 `session_id`、`actor_id` 和快照版本，模型只提交行动种类、目标、必要参数、可见依据事件和一句简短意图。Pydantic 使用按行动类型区分的结构校验，再由规则检查地点、归属、权限和行动前提。依据事件必须属于该角色可见事件。

玩家以明确的动作按钮为主，自由文本默认对选中对象说话；选择“执行行动”时才解析成提案并展示确认，模糊表达不直接消耗回合。基础观察可免费查看已经可见的信息；会改变世界的合法动作和交谈各推进一回合。

### 信息隔离

- 世界事实：真实位置、持有人、设备状态等，由程序维护。
- 可见事件：依据当时的位置、听觉范围和对话对象计算接收者，投递后保留接收记录。
- 角色记忆：区分亲眼观察、听人转述和自己判断，保留来源事件。
- 私有目标：只进入本人模型上下文与调试接口。

公开谈话向同地点角色投递；私语只向参与者投递；普通声音不跨地点。是否看见移动、交付等事件按明确感知规则计算。玩家也有独立投影，正常 API、SSE 和结算都不能顺带返回全体角色的秘密。

角色说“镇长已经同意”只产生一条陈述事件，不更改摊位状态。角色转述会创建新的陈述事件；能建立的来源关联由服务器核对，不能把角色未见过的事件塞入依据链。

短局先保留完整结构化记忆，模型输入使用最近若干条与当前任务相关的可见记录，并始终带上未完成工作及承诺；截断只影响本次上下文，不删除存档中的原始事件。不先做自动摘要与长期遗忘。

### 回合流程与冲突处理

1. 校验玩家动作。合法动作在事务内写入状态、事件和回合运行记录；前端重复提交同一 `request_id` 不再执行。
2. 生成玩家行动后的快照 V，向可感知者投递事件。
3. 唤醒收到新信息、有未完成工作、到达重考虑期限的角色。每轮最多四个，每人最多一个提案；不需要依赖玩家点名才能行动。
4. 各角色基于同一快照 V 并发决策。未选中的角色本轮等待，未读信息保留到下一次唤醒。
5. 收集提案后，由一个裁决器开启短事务，确认世界仍为 V，再按可复现的轮换优先级逐个重新检查前提、应用结果。
6. 状态变化、成功或失败事件、记忆投递与回合完成标记在同一事务提交，再向客户端发布。
7. NPC 行动引发的新反应留到下回合，避免一回合内无限对话；最后检查结局。

**不能每提交一个 NPC 就用全局版本变化拒绝其余同批提案。** V 用于检验批次快照是否过期，同批中的竞争由逐动作前提复查处理。两人拿同一物品只有一个成功，互不相关的合法行动都应生效。

单局同一时刻只运行一个回合；操作中禁止再次推进。重启后已完成回合直接恢复，进行中回合按已落库提案继续，未返回的调用可以补发；任何迟到结果须核对回合与角色决策标识，不能写入下一回合。远端调用补发可能产生额外模型费用，但游戏动作不能重复提交。

## 6. 数据与 API 草案

数据结构按职责分开，不追求第一天就设计通用世界编辑器：

| 数据 | 主要用途 |
| --- | --- |
| `game_sessions` | 场景配置版本、角色目标版本、当前回合、状态、世界快照和版本 |
| `turn_runs` | 请求幂等键、回合阶段、基准版本、处理中或已完成状态 |
| `world_events` | 递增事件序号、行动者、类型、内容、原因事件引用 |
| `event_recipients` | 事件在发生时向谁可见，保证历史查询与实时投递一致 |
| `character_memories` | 所属角色、来源事件、观察/转述/判断、结构化内容 |
| `action_proposals` | 提案、对应回合与角色、基准快照、裁决结果及失败原因 |
| `llm_calls` | 角色、状态、延迟、token 用量、实际提供给模型的上下文与响应 |

小世界的人物位置、物品、设施和工作进度先放进带版本的结构化快照；静态场景使用 YAML 配置。状态与事件同事务保存，按回合保留快照，避免首版就实现复杂事件溯源框架。

主要接口建议：

```text
POST /api/games                         创建新局，接受可选角色目标覆盖
GET  /api/games/{id}                    读取玩家可见状态
POST /api/games/{id}/actions            提交结构化动作和幂等键
GET  /api/games/{id}/events?after={seq}  SSE：补发历史并继续推送
GET  /api/games/{id}/turn               查询当前回合执行阶段
GET  /api/debug/games/{id}              完整调试状态、调用与认知对比
POST /api/games/{id}/restart            根据同一场景配置创建新局
```

调试端点单独开关，默认服务仅监听本机。玩家事件游标支持序号空洞，不因看不到某条私有事件而卡住续传；调试推送与玩家推送必须经过不同的投影入口。

      storage/         # 数据库、迁移、快照与事件
    scenarios/festival.yaml

## 7. 开发顺序与每一步的验收

以下是熟悉 Python / React 的单人有效开发时间估算，未计入学习环境、等待账号和大幅美术调整。总计约 **8—13 个工作日**，以阶段验收修正，不当作工期保证。

| 阶段 | 工作内容 | 可交付结果与通过条件 | 估算 |
| --- | --- | --- | --- |
| P0：规则定稿与骨架 | 配置场景，写类型和规则，定义18回合及信息范围，后端启动和数据库迁移 | 无模型、无 UI 也能用动作序列完成开幕；失败路径不破坏状态 | 1—2天 |
| P1：手动可玩的世界 | 地图、玩家操作、回合、SSE、存档恢复；开发入口手动操控 NPC | 浏览器能完整玩完并重开，刷新不丢状态，双击不会重复推进 | 1—2天 |
| P2：一个真实角色 | 先接店主，加入私有目标、可见上下文、结构化行动和调用记录 | 自由谈判会影响其提案；非法输出与超时可处理；其余 NPC 暂由开发入口控制 | 1—2天 |
| P3：四角色联动 | 独立记忆、唤醒机制、同快照并发决策和串行裁决 | 不依靠玩家逐一指挥也会行动；私语不泄漏；竞争物品没有重复持有 | 2—3天 |
| P4：反复试玩与调试 | 调试页、开局修改动机、历史回合、用量和延迟统计、恢复进行中回合 | 可对比同一场景不同目标的行为，并追溯行为依据；重启可继续 | 1—2天 |
| P5：玩法与交付 | 调整回合数和上下文，完成真实模型试玩、启动说明与配置样例 | 完成验收清单，能够按说明在本机启动、配置模型和反复开局 | 1天 |

依赖顺序为 P0 → P1 → P2 → P3 → P4 → P5。先让真实模型参与单角色试验，再投入四角色与调试页面的完整开发；如果店主阶段持续只聊天不行动，应先修行动空间、上下文和动机，暂停扩角色。

若实际只有两天，目标缩为“三地点 + 一个真实 Agent + 其余角色人工控制 + 基础事件面板”，明确标注演示范围；不把这一版本描述成四个自主角色的完成品。

## 8. 延迟、费用与异常处理

- 每个被唤醒角色正常只调用一次决策，避免多轮工具循环；结构错误最多一次修复，仍失败则等待并记录原因。
- 暂定单次调用 10 秒超时、整轮 15 秒总期限，修复与重试共享期限；具体阈值根据 P2 的实测修改。
- 超时、断网、限额或空响应不生成剧情性动作，只产生等待或可重试状态；调试页显示真实原因。
- 等待期间界面显示谁正在决策、谁已完成；不展示尚未裁决的台词为已发生事件。
- 18 回合四角色每轮都唤醒时，基础上限为 72 次 NPC 决策；解析玩家动作、输出修复和失败补发另计。常规局通过事件唤醒减少调用。
- 按调用记录实际输入、输出与用量；费用按所选供应商单价估算，并区分供应商缺失用量的情况。P2 后给出每局调用量与费用测算。
- 目标是常规回合约 3—8 秒内完成，这是体验目标而非模型性能保证；若真实端点达不到，先降低调用量、上下文和模型延迟，不扩地图和角色数。

## 9. 关键验收与测试策略

自动化测试重点放在确定规则和异常，不断言角色一定说某句话：

- 同一物品只有一个位置或持有人；不同地点不能交付、偷听或操作设施。
- 同批两个角色争抢物品只有一个成功；两个互不冲突的动作可以同时生效。
- NPC 与玩家正常接口都无法取得未投递的秘密；SSE 重连和历史查询也遵守这一点。
- 台词、谎言和模型宣称的结局不改变设施、物品或胜负。
- 摊位只能由有权角色确认；检查和安装必须满足前提，工作进度按回合累积。
- 重复请求、模型非法输出、调用超时、迟到结果和进程重启不会重复执行行动。
- 每次世界变化都有事件；快照、事件、记忆投递与回合完成标记保持一致。
- 到期结局由最终状态计算，边界包含最后一回合完成安装的情况。

真实模型试玩至少覆盖三类输入，每类进行多局记录，评估其差异及失败原因：

1. 正常合作：玩家帮助解释争议，观察角色是否自行协调。
2. 改变动机：店主目标改为“尽快关店接孩子”，规则不变，检查它是否改变行动优先级；不要求每局采取同一策略。
3. 传播与核实：只向店主私语一个说法，对比镇长、记者是否在收到转述前获知；再检查转述与核实的来源。

完成标准是玩家可以影响有独立打算的角色，角色能够执行真实动作，局势变化能够追溯，同时世界规则始终成立。不能把“每局文案不同”当成自主性验收。

## 10. 版本推进与下一步

规划完成后，已确认采用可配置模型 API 与俯视像素小镇，并开始独立实现。实际实现未使用 ARTEX 的代码或服务。

开始实现时，第一批任务应是：

1. 创建 Python / React 工程与运行说明，选定一个可用的模型端点。
2. 固化 `festival.yaml`、行动类型、感知规则和胜负条件。
3. 实现纯规则引擎、SQLite 快照与事件事务，验证一局可完成。
4. 做最小地图和明确动作入口，进入 P1 手动试玩。

P3 通过后再决定是否加入更丰富的承诺、关系变化、像素美术及主持延时等交互；公开发布所需的账号、多用户隔离、部署和运营单独规划，不混入本地原型工期。
